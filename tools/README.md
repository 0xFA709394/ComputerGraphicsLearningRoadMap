# tools/ —— 可复现的验证方法论

本仓库每个示例 README 里的"已验证"都来自这套工具链。原则：**验证器也是交付物**。

## 工具

| 工具 | 用途 |
|---|---|
| `verify-all.sh` | 一键跑全仓库可自动化验证（C++ 产物断言 + 控制器单测 + Metal 构建） |
| `pngview.py` | PNG → ASCII 亮度图（纯标准库）——无屏环境"看"渲染结果 |
| `tga_stats.py` | TGA 产物断言：亮像素下限 + 定点颜色探针 |

## 方法论（三条铁律的来源）

1. **统计先于肉眼**：亮像素占比、定点探针、单调性断言——比"看起来对"硬一个数量级。
   血泪史：14 号的"地面消失"疑案 = 检测器量程标错 + 验证器补丁链腐化的双重假象（见 code/14 README）。
2. **检测器要标定**：量程必须用已知样本验证（渲染灰 130 却统计 60~110 = 白忙一场）。
3. **验证器会腐化（四种已观测形态）**：①检测器量程标错；②多代补丁后行为漂移；③内嵌的示例代码副本过期（修复只进了仓库没进 harness）；④修复"在验证器里试过"但从未落库。对策：**harness 从仓库源码即时生成**（见 code/16~21 的 headless 驱动生成脚本），绝不手工维护副本。

## 已知问题登记（验证器抓出来的）

- **code/16 的 radixScatter 覆盖丢失**（driver16base.swift 抓出）：独立驱动下排序后大量槽位互相覆盖（16 元小例覆盖 4/16）——散射游标的初始化/同步存在缺陷（已试：GPU 侧游标初始化绑定，未愈）。**根因候选清单**：① clear→hist 无栅栏竞态；② scan 的前缀和未含"本轮 hist"的时序；③ 散射与 scan 的 buffer 别名。修复方向：改双缓冲分段散射或参考工业实现（案例 D 第 11~12 周）。示例自带的 SIMD4 路径（16 号 GUI）未暴露此问题——**两条测试路径的又一实证**。
- 教训：示例内嵌验证（SIMD4 路径）与独立驱动（metallib 直驱）是**两条不同的测试路径**——都过才算过。

## Metal GUI 示例的验证边界

无人值守环境（CI/SSH）无法运行 GUI。可自动化的部分：
- **构建**：`build-all.sh`（CI 可跑）
- **离屏渲染**：示例的 `offRpd` 钩子模式（见 code/16~21 的 headless 驱动写法）——渲染到纹理后回读断言
- **纯逻辑**：可注入合成输入的控制器（DRS 为范本）单测

人工部分留给 `build-all.sh --run`（GUI 冒烟）与 Xcode GPU Debugger（帧捕获级排查）。
